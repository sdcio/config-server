# 03 — Self-heal `TargetForConfig` condition on no-op reconcile

**What to build:** See `../spec.md` for the full spec (Solution item 2, Implementation Decisions second bullet, Testing Decisions second bullet). This is the diagnosis's PR-description-worthy fix on its own — it's expected to resolve the observed CI symptom (`Config Check Ready` timing out) regardless of what ticket 02's investigation finds.

`TargetConfigController.Reconcile`'s `!hasChanged` early-return path (currently `pkg/reconcilers/targetconfig/reconciler.go:239-242`: `log.Info("Transact skip, nothing to update"); return ctrl.Result{}, nil`) should unconditionally call `r.cfgMgr.SetConfigsTargetConditionForTarget(ctx, targetOrig, configv1alpha1.TargetForConfigReady("target ready"))` before returning — the same call/value the success path already makes at line 309 — instead of silently leaving whatever `TargetForConfig` condition a prior reconcile set untouched.

This is confirmed safe both procedurally (this point is only reachable after the `IsReady()` (line 177), `dsctx`/`dsctx.Client` (lines 184-200), and `Recovered` (line 201) gates earlier in the same `Reconcile` call have already passed, so "target ready" is the function's own already-established finding here, not an assumption) and at the `Config` level (`SetOverallStatus`/`GetOverallCondition`, `apis/config/v1alpha1/config_helpers.go:216-258`, compute overall `Ready` as `ConfigReady AND TargetForConfigReady AND resolverOK` — three independent conditions, so this change can't mark unapplied content as applied). `SetConfigsTargetConditionForTarget` (`pkg/sdc/target/manager/configmanager.go:223-247`) already no-ops the API write when both the target condition and the resulting overall `Ready` are unchanged, so calling it unconditionally here adds no extra API traffic in the steady state.
