# 02 — Requeue-delay investigation logging (best-effort, non-blocking)

**What to build:** See `../spec.md` for the full spec (Solution item 3, Implementation Decisions third bullet, Testing Decisions third bullet). Investigate, best-effort, why `TargetConfigController`'s `RequeueAfter: 5 * time.Second` (`pkg/reconcilers/targetconfig/reconciler.go` lines 180-181/188-189/194-195) is, per the CI evidence in `spec.md`, sometimes honored ~20x late (observed ~103s instead of ~5s) even with `MaxConcurrentReconciles: 16` configured.

Add structured log lines at the point `ctrl.Result{RequeueAfter: ...}` is returned (capturing the scheduled fire time, keyed by target name) and at `Reconcile`'s entry (capturing actual entry time, same key), so a log diff can directly show scheduled-vs-actual delay per key. This ticket does not need to fully explain the delay to be considered done — tickets 01 and 03 already make the system self-heal regardless of it.

## Comments

- Split out from the original combined ticket (item 1) after a `/to-tickets` pass, per the spec's framing of the three changes as independently-useful and stackable. See `../spec.md` for full context and provenance (filed from CI evidence gathered validating `sdcio/config-server` PR #476 / `sdcio/data-server` PR #471).
- **Implementation:** added a `reconcile-entry` log line right after `ctrl.Result`/`log` setup in `Reconcile` (before the `Target` fetch, so it fires on every invocation including early-return paths), and a `requeue-scheduled` log line — via a new `logRequeueScheduled` helper — at each of the four target-readiness-gate points that return `ctrl.Result{RequeueAfter: 5 * time.Second}` (`!targetOrig.IsReady()`, `GetDatastore` miss, nil `dsctx.Client`, and `!dsctx.Status.Recovered`). All four are covered, not just the three cited in the spec/ticket text, since they're the same readiness-gate class of event and the extra one (`!dsctx.Status.Recovered`) closes what would otherwise be a gap in the per-key diff. Both log lines are keyed by target name/namespace; `requeue-scheduled` also carries the specific gate `reason` and the computed `scheduledFireTime` so a log query can pair it with the next reconcile's `reconcile-entry` time for the same key to get exact scheduled-vs-actual delay.
- **Investigation outcome: inconclusive, as anticipated — best-effort only.** No CI/containerlab access this session (same constraint noted at ticket-authoring time), so the new log lines could not be exercised against a live ~103s-delay repro. Static review of the surrounding code turned up one plausible (not confirmed) contributing factor worth flagging for whoever does the CI soak-test follow-up: `MaxConcurrentReconciles: 16` (`cmd/controller/main.go:116`) is set once on `ctrl.Options.Controller`, which controller-runtime applies as the *default* for every controller registered via `ctrl.NewControllerManagedBy(mgr)...Complete(r)` that doesn't override it per-builder (`WithOptions`) — none of the controllers in this repo (`targetconfig`, `targetdatastore`, `targetrecovery`, etc.) override it, so each gets its own independent pool of 16 workers rather than sharing a single pool. That rules out cross-controller worker starvation as a cause. Within `TargetConfigController`'s own 16-worker pool, though, each `Reconcile` call that reaches the transact path blocks synchronously on `r.transactor.Execute`/`Confirm` (gRPC round-trips to the dataserver, `reconciler.go` `Execute`/`Confirm` calls), so a burst of concurrently-enqueued keys (e.g. from the `SensitiveConfig`/`Config` watches firing across many targets during the CRUD test's write burst, per the spec's cause 1) could plausibly tie up all 16 workers for longer than 5s each, delaying a newly re-queued key's next pickup well past its scheduled fire time. This is consistent with, but not proof of, the ~103s observation. The new log lines plus the already-exported `workqueue_depth`/`workqueue_queue_duration_seconds` metrics (labelled by controller name, from `cmd/controller/main.go:95-111`) are exactly the tools needed to confirm or refute this during the CI soak-test follow-up: a `requeue-scheduled` entry whose paired `reconcile-entry` is ~100s late *and* a coincident spike in `workqueue_queue_duration_seconds{controller="TargetConfigController"}` would confirm worker-pool saturation as the cause; a late pairing with a flat/low queue-duration metric would point elsewhere (e.g. GC pause, client-side rate limiting, or the underlying informer/watch cache).
